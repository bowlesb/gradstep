# Original-paper acquisition — migration 011 candidate

Status, 2026-10-03: **local SQL candidate and fixture tests implemented; not deployed and not a live acquisition workflow**. Migration 010 is applied to staging and immutable. The candidate keeps metadata, originals, verification, and original reads disabled, with no verification profile or credential installed. Root and independent reviewers examined the design and SQL; review-driven regression results are recorded below. Network/Storage adapters, attestation ingress, hosted runtime admission, and native/web read integration remain required before live use.

011 should deliver bounded arXiv metadata resolution, a truthful source-only outcome, and acquisition/publication of eligible original PDFs. 012 should separately implement complete Mathpix authorization, submission reconciliation, result-bundle publication, and settlement. The final reader requires Mathpix equations, text, figures, and offline assets; an original PDF is an intermediate capability. No part of 011 enables the legacy unquoted OCR path.

## Observable contract

An authenticated native or browser client continues to call `v2_begin_import` with a normalized arXiv base ID, optional revision, operation ID, and its caught-up library cursor. It displays that durable import beside existing papers. The acquisition scheduler discovers accepted imports from the database; an HTTP enqueue acknowledgement or Realtime message is never the only record of work.

| Outcome | Library behavior | Network/cost behavior |
|---|---|---|
| Valid metadata; supported, verified version-specific reuse evidence | Pin the metadata/version, acquire or reuse exact bytes, then resolve through 010 | Reserve original-storage and transfer capacity before downloading; no OCR credit hold |
| Valid metadata; unsupported or unverified reuse rights | Finish `source_only`, with title, authors, source categories, date, canonical abstract link, and reason | Do not download or redistribute the PDF; no OCR call |
| Exact approved original already available | Resolve the import to that immutable original, preserving any established item/artifact pins | No new original download or OCR charge |
| Existing compatible, fully published conversion | Resolve using the same exact document and verified artifact | Reuse is free; compatibility and complete-bundle verification remain required |
| Temporary metadata/download problem | Keep the row, bounded retry deadline, and typed recoverability | Retry only that stage, within shared limits |
| Cancel, Remove, or newer intent wins | Late completion may populate the shared catalog, but cannot recreate that account's membership | Detach this interest; another account's interest remains valid |
| No surviving interest before a network claim | Park/finish unstarted work without downloading | A cancellation racing an already-authorized free transfer can leave a bounded orphan; it does not authorize paid work |

Do not turn missing/invalid metadata into an empty search result or a readable paper. Do not let a failed asset request remove the saved paper. `ready` in 010 means membership resolution succeeded; the original/conversion capability is separate. Public categories remain source metadata; private labels and generated private descriptors are outside this acquisition job.

## Proposed durable records

These names are implemented in the local candidate; they are not claims about hosted tables. Keep internal tables outside exposed schemas, with no direct anon/authenticated writes. Service RPCs use explicit arguments, empty search paths, constrained grants, and bounded JSON. Foreign keys and their implicit locks belong in the lock review.

| Record | Required identity and fields | Ownership / invariants |
|---|---|---|
| `acquisition_policy` | Singleton; enabled environment; metadata/original enable switches; current adapter and validation profiles; row/byte/attempt/age caps | Starts disabled. Serializes job/receipt capacity; never grants paid-provider authority |
| `acquisition_source_slots` | Unique `(source_id, requested_revision_or_zero)`; lookup generation; active/cached lookup job; successful observation time and freshness deadline | Zero means an unversioned lookup, not version zero. A completed lookup is not a permanent answer to “latest” |
| `acquisition_jobs` | UUID; kind `lookup` or `original`; immutable input digest; source/version/profile key; stage/status and committed `state_revision`; output references; generation, claim ID, lease/deadline, next attempt, counters, bounded error | Lookup identity is `(slot, lookup_generation)`. Original work has at most one active job for `(version_id, reuse_policy, acquisition_profile)`. Terminal output pins cannot be overwritten |
| `acquisition_steps` | Unique `(job_id, operation_id)` and request digest; stage/generation; network/storage attempt reference; timestamps; bounded result digest and code | Durable receipts for side effects and acknowledgements. Same operation/digest reconciles the prior attempt; different input conflicts. Counts are capped, including failures |
| `acquisition_commands` | Immutable operation ID, request digest, chosen job | Coalescing and expired cache observations cannot change the job returned by a replay; included in control admission |
| `acquisition_interests` | One row per `(account_id, import_id)`; captured `intent_revision`; lookup/original job references; separate last-projected lookup/original revisions and import state sequence | An account relationship, not ownership of global work. Retry replaces the captured revision after validation; old worker tokens remain stale. The current 010 import is authoritative |
| `arxiv_network_gate` | One authority-wide row; environment identity; token/generation; attempt ID; opened/closed times; `next_allowed_at`; hard recovery deadline | Coordinates all controlled arXiv callers, not one independent row per project. Initial authority is staging only |
| `paper_storage_capacity` | Singleton counters and configured bounds for retained and reserved bytes/object count; transfer windows with issued reservations; committed environment-wide asset-state sequence | Includes pending, uncertain, quarantined, verified, and deleting objects. Separate from support storage and OCR credits; reconstructible from reservation/publication records |
| `paper_asset_reservations` | UUID; original job/attempt; generated private-bucket path; maximum bytes; actual candidate hash/length; verification result/profile; expiry, generation, lifecycle, final object ID | Exists before document identity is known. No overwrite; only the owning fenced worker can complete it. No account owns a shared original |
| `paper_verification_profiles` | Immutable profile ID/digest; parser/build identity; format policy and hard input/decompression/object/CPU/memory/wall limits; authorized verifier identity | A replaceable verifier contract, not an assertion that a particular PDF library is safe. Deployment selects an enabled, measured profile |
| `paper_verification_results` | Immutable `(reservation_id, generation, profile_id, operation_id)` receipt; verified stored hash/length/page count; bounded structural outcome and timing; authenticated verifier identity | Only the configured verifier can attest; the job publisher cannot substitute a client/provider estimate. Results bind the immutable candidate bytes and current fenced request |
| `paper_integrity_failures` | Immutable expected candidate binding and complete/incomplete observed hash/length facts | Storage mismatch or oversize quarantines without asserting structural success; incomplete input has no whole-object digest |
| `paper_originals` | One canonical original per shared `document_id`; immutable `stored_object_id`, verification profile/evidence, publication time | Unique exact-byte document wins. Existing 010 approvals keep their original object pointers; a canonical choice never rewrites them |
| `paper_asset_availability` | Object ID; revision from the committed environment asset-state sequence; `available`, `unavailable`, or `quarantined`; checked time and bounded reason | Mutable operational state beside immutable byte identity. An unavailable published object is retained, not silently replaced or marked usable |
| `paper_availability_outbox` | At most one dirty work row per document; current target revision, pass revision, stable recipient scan cursor, claim generation | Durable, coalescing notification obligation. Newer state cannot erase an unfinished pass; account projection is a separate transaction |
| `library_asset_projection` | Account/item key; pinned original/artifact IDs; last applied availability revisions; stored `original_availability` / `render_availability` | Changes atomically with the item's `state_seq` and full `library_changes` entry. Does not change membership intent or choose a new artifact |

Keep lookup and original jobs separate. Concurrent `1234.56789` and `1234.56789vN` lookups may require separate metadata observations; once both pin the same eligible version they attach to the same active original job. Aliases with different versions are not collapsed. At publication, equal verified SHA-256 bytes converge through the shared-document uniqueness constraint, even if two distinct version jobs downloaded them. This does not promise one metadata request or one PDF transfer across every alias; it does prevent duplicate canonical originals and preserves the exact-byte key used by later OCR.

An original job returns document/object identity, not a universally interchangeable approval. Each lookup needs an approval whose `metadata_id` matches that import's immutable pin. Reuse the original bytes and the applicable retained rights evidence, then create/reuse the corresponding 010 approval in a separate ordered catalog transaction before account resolution. Passing a different lookup's approval to `worker_resolve_import` is a source mismatch, even when both observations describe the same version.

Catalog metadata, source versions, version-document associations, approved evidence, documents, and verified stored objects reuse 001/010 identities. Do not add another mutable “paper” record containing all of them. In particular, `stored_objects` requires a document for `paper-assets`; use the separate reservation while the hash and page count are unknown, rather than inserting a fictitious document.

## Metadata, version, and rights resolution

1. Validate the input with the shared arXiv adapter. Persist only the normalized base ID and optional positive revision. Derive all outbound URLs internally; never fetch the submitted URL, arbitrary URLs from XML, redirects to arbitrary hosts, or customer-supplied license evidence.
2. Join a live lookup for the same normalized reference, or use a successful cache entry whose freshness permits it. Proposed beta freshness: 24 hours for an unversioned “latest” observation; negative/transient outcomes are not a successful cache. After expiry, allocate a new lookup generation. An import already pinned to version N stays on N, even if the next lookup finds N+1.
3. Fetch a single-entry Atom response through the global gateway. The existing parser bounds decoded XML to 1 MiB, validates namespace/identity, rejects DTDs, and limits depth, nodes, attributes, authors, and categories. Transport must additionally cap encoded bytes, redirects, and duration; parser limits alone do not bound network work.
4. In one checkpoint transaction, record the validated metadata through `worker_record_arxiv_metadata` and bind the lookup's exact version/metadata. Retain full Atom timestamps in the lookup observation for license correlation. **Map only the catalog DTO's date fields to `YYYY-MM-DD`**: 010 rejects full ISO timestamps. Keep the date-only catalog payload within 32 KiB and the adapter's stricter 30,000-byte bound. A crash cannot leave an import pin inferred from an unrecorded HTTP response.
5. Fetch the internally derived arXivRaw/OAI record. The current adapter permits shared reuse only for its exact CC0/CC-BY 4.0 allowlist, with matching source ID, latest revision, and latest-version timestamp. A latest-version license is not evidence for an older pinned PDF. Store normalized evidence, response SHA-256, source URL, observed time, adapter/policy version, and the exact metadata association. The response hash records provenance; it is not an arXiv signature or a PDF hash.
6. On a valid response with missing, unsupported, or unverified rights, checkpoint `source_only` with the 010-compatible `license_unverified` code and a bounded additive detail code (`revision_unverified`, `license_unverified`, `license_not_supported`). Link to the canonical abstract page. A network error is a retryable metadata failure instead; it must not be misreported as a license decision. An older version can use already-retained approval evidence for that exact version, if still allowed by policy; otherwise it remains source-only.
7. If eligible, attach to ready exact-version/byte evidence or the active original job. The import changes to `acquiring` with the same metadata pin. A later metadata refresh may create a new catalog observation; it cannot replace that import's metadata or bytes.

The source's metadata reuse permission does not grant permission to distribute its full text. The first slice deliberately narrows supported full-text rights; other rights/private acquisition require a separate reviewed path. [arXiv API terms](https://info.arxiv.org/help/api/tou.html), [license and version information](https://info.arxiv.org/help/license/index.html), [OAI metadata interface](https://info.arxiv.org/help/oa/index.html).

No raw source responses, arbitrary exception text, account identifiers, or private content go to application logs. Persist bounded typed diagnostics and correlation IDs. The trusted acquisition adapter, not a client's JSON assertion, establishes external-source provenance.

## One outbound arXiv authority

The arXiv API/OAI/RSS rate rule is aggregate across controlled machines: at most one request every three seconds and one connection at a time. Two project-local limiters cannot meet it. [arXiv API rate limits](https://info.arxiv.org/help/api/tou.html)

Initially, **only the staging acquisition gateway may make automated arXiv requests**. Production, local workers, tests, feed refresh, and other source adapters use fixtures or the same gateway. Before enabling a schedule, inventory any still-running legacy Science Reader arXiv caller; this plan does not authorize stopping or modifying the NAS. A second outbound environment remains disabled until a single narrow shared authority is in place. That authority accepts normalized source operations with byte/deadline limits, not arbitrary URLs or either project's service-role key. Moving the authority requires a drained, quarantined handoff; restoring a backup must not create a second live gate.

Apply the same conservative serialized gate to Atom, OAI, and PDF requests, including retries and each accepted redirect. Automatic redirect following is off; an allowed redirect is a new recorded request with a finite hop limit. Each connection is closed/aborted before release; the HTTP implementation must demonstrate its connection behavior, including keep-alive. `next_allowed_at` is at least **three seconds after confirmed connection closure**, and no next request starts while the preceding connection may remain open. SQL permit-grant time is insufficient because the actual fetch can start later. A 429/503 `Retry-After` can extend the gate; it cannot remove normal spacing. Unknown closure uses the conservative hard-recovery boundary plus spacing, and a changed owner-lifetime assumption fails closed.

`worker_claim_arxiv_stage(job, claim_id, environment, reservation_id?)` atomically commits the fenced source-stage claim, one-use network permit, attempt count, transfer ceiling, and (for originals) upload ownership. Gate contention/cooldown returns `wait` without creating a receipt, changing job generation/revision/attempts, changing a reservation, or charging transfer capacity. A digest binds all four arguments; changed replay conflicts even after the stage advances, while exact replay/status never grants a second fetch. Commit the grant, perform the bounded request outside SQL, close its body, then acknowledge completion. If permit creation or the fetch result is uncertain, query the attempt. If the process disappears without closure proof, retain the gate until the old invocation's hard termination boundary plus grace; ordinary SQL lease expiry is insufficient. A resumed worker past its request deadline must stop before opening a connection.

Use one short invocation per stage, with an application deadline at most 120 seconds. On the currently documented paid Edge runtime, the worker's maximum lifetime is 400 seconds; the initial conservative gate recovery bound is **450 seconds from permit grant**, subject to a deployment test proving that the connection-owning invocation cannot outlive that bound. Do not assume a returned 504, an expired job lease, or a background task means a request ended. If that bound cannot be established for the chosen HTTP runtime, keep the gate quarantined and use a gateway with enforceable termination. [Supabase Edge limits](https://supabase.com/docs/guides/functions/limits)

The gateway must not issue a transferable long-lived permit to an arbitrary process that could open a connection after this horizon. It owns the fetch in the same bounded invocation. No database transaction remains open during a wait, fetch, upload, or verification pass; workers return a durable `next_attempt_at` rather than sleep through the rate interval.

## Original reservation, validation, and publication

Before a download, reserve the admitted maximum bytes and one object, plus the complete attempt's source/storage transfer allowance. Unknown `Content-Length` does not mean unlimited capacity. Count actual streamed bytes and stop at the limit; headers are not authority. An oversized body, HTML/error page, decompression expansion, truncation, or unsupported PDF cannot become a document.

The proposed pilot profile admits at most **5 MiB and 50 pages per original**, tightened to match the isolated qpdf/WASM prototype under investigation. It stays disabled until that exact build's metrics and limits are verified. This is a beta admission limit, not the 32 MiB/250-page schema ceiling or a promised product limit. Standard Storage upload is recommended for files up to about 6 MB; larger-file support should use a separately tested resumable protocol and verification worker. Paths are server-generated from reservation IDs and written without upsert. [Supabase upload guidance](https://supabase.com/docs/guides/storage/uploads/standard-uploads)

| Reservation transition | Required evidence / retry rule |
|---|---|
| `reserved → uploading` | Atomic source claim + permit; current live interest, reserved byte/count/transfer headroom; fixed generated path and extended `safe_after` writer horizon |
| `uploading → pending_verification` | Successful bounded transfer; candidate digest and length recorded |
| `uploading → upload_uncertain` | Timeout/lost response; keep the reservation and immutable path |
| `upload_uncertain → verifying` | Wait beyond the prior writer horizon; reconcile the same path and candidate identity under the configured verifier |
| `pending_verification → verifying` | Configured verifier obtains a fenced claim and bounded object access; its retries/transfer allowance remain separate from acquisition |
| `verifying → verified → published` | Authenticated immutable verification result proves stored bytes/structure/page count; a separately claimed publisher validates source/approval and commits canonical output |
| Unpublished failure → `quarantined` | Preserve typed reason and occupied/reserved capacity until controlled cleanup |
| Unpublished expired → `deleting → deleted` | Old writers fenced and past the hard lifetime/grace; Storage absence confirmed before releasing capacity |

An uncertain upload reconciles the existing path first. If absent, a current claim may retry the same no-overwrite operation within its attempt budget. If bytes differ from the recorded candidate, quarantine; never replace them. An ambiguous prior writer must be past its hard lifetime before a new upload attempt or janitor can claim that path. Separate transfer receipts prevent repeated verification reads from becoming unmetered egress.

Validation must parse the **stored** bytes with a bounded PDF parser: actual SHA-256/length, supported PDF structure, encryption/password status, cross-reference/object/decompression limits, and actual page count in 1…250. A `%PDF` prefix, MIME header, filename, HTTP length, regex over `/Page`, client page count, or provider estimate is insufficient. Record parser/profile version and the verified facts. Reject malformed, encrypted, over-limit, or unsupported files explicitly; do not invent a page count or silently repair bytes under the original hash.

Treat verification as a replaceable durable worker boundary. Acquisition may download/hash/upload within its admitted limits, but the reservation stays `pending_verification` until a configured verifier supplies a fenced result. A verifier receives only a scoped reservation/hash/profile request and bounded private-object access. Its result binds the exact stored bytes, profile/build, operation, and claim generation. Authenticate that narrow result endpoint independently; a customer, general import callback, or arbitrary service JSON cannot assert trusted page count. An isolated verifier does not need a general Supabase service-role key. Expired/foreign/profile-mismatched results cannot publish; a lost valid acknowledgement is recovered from its immutable result receipt.

Supabase Edge currently has 256 MB memory and 2 seconds of CPU per request; asynchronous I/O time is excluded from that CPU allowance. These limits make a 32 MiB/250-page SQL constraint inadequate as a runtime admission policy. [Supabase runtime limits](https://supabase.com/docs/guides/functions/limits)

Benchmark the proposed parser against representative equation-heavy papers, large compressed object streams, adversarial cross-reference graphs, invalid documents, and maximum admitted bytes. Record peak RSS and CPU, with headroom. Split downloading, verification, and publication into separate invocations. Input/page caps or a library's “strict” flag, including pdf-lib's, do not establish bounds on decompressed structural streams. `original_enabled` stays false until a measured profile passes. Candidate implementations include an isolated qpdf-based process outside Edge or an actually bounded WASM parser; neither is approved by name alone. If the needed range cannot fit, use an isolated compute worker with explicit CPU/memory/wall limits and the same reservation/claim contract; choose hosting inside the approved budget before provisioning it. That is an implementation/measurement gate, not a reason to accept unverified originals.

Publication is one short global transaction after verification: recheck the current claim/reservation and eligibility; lock capacity and the exact-byte document identity; create or reuse the immutable shared document; establish the verified version-document relation; register the verified stored object and canonical original; create/reuse the 010 approval; mark current availability; and enqueue the availability obligation. Same publication operation returns the same IDs after a lost response. No library account is locked in this transaction.

If the hash already exists, length and page count must agree with that immutable document. A mismatch is a verification conflict, not an `UPDATE documents` opportunity. If the canonical original already exists and is available, reuse it; the losing newly uploaded object remains an unpublished orphan until safely deleted. Existing approvals/artifacts retain their own pinned objects. Never repoint a verified object, approval, document, or artifact to a different file to make a retry succeed.

## Worker RPCs and recovery

These candidate service APIs supplement, rather than rename or weaken, 010. Side-effecting acquisition calls have stable operation ID/digest receipts, bounded output, and current-state inspection. The narrowly defined operational availability observer uses revision-CAS semantics described below instead of an unbounded receipt history. Global-job transitions check a current generation, unexpired lease, expected stage/revision, and fixed inputs. Unknown acknowledgements are reconciled before choosing another operation.

| Candidate API | Commit boundary / response |
|---|---|
| `worker_import_state(account_id, import_id)` | Read current 010 phase, state sequence, intent revision, desired presence, source/metadata pins, and acquisition links; never return another account's data to a customer |
| `worker_scan_acquisition_imports(after_account?, after_import?, limit=50, metadata_only=false)` | Bounded deterministic scan of imports needing linking/projection/retirement; metadata-only mode suppresses only already-projected eligible work waiting for an original, preserving all other obligations |
| `worker_prepare_acquisition(operation_id, source_id, requested_revision?)` / `worker_prepare_original(operation_id, lookup_job_id)` / `worker_retry_lookup(operation_id, previous_job_id)` | Under global job capacity, create/reuse lookup or eligible original work. Return immutable inputs and job state; no outbound call and no account membership mutation |
| `worker_link_import_acquisition(account, import, expected_intent_revision, expected_state_seq, lookup_job, original_job?)` | Account transaction validates identical source/version and current intent, then captures interest and appropriate 010 checkpoint. Linking a job does not authorize a paid operation |
| `worker_claim_acquisition(job, claim_id)` / `worker_acquisition_state(job, operation_id?)` | Fenced `reserve`/`publish` claim or replay/status result. Source stages return `source_claim_required` without mutation; verification has its own authority |
| `worker_finish_lookup` / `worker_fail_acquisition` / `worker_record_original_upload` | Validate the stage-specific schema; atomically pin metadata/evidence or save the next stage/result and outbox obligation. Late workers cannot replace pins |
| `worker_claim_arxiv_stage(job, claim_id, environment, reservation_id?)` / `worker_finish_arxiv_request` / `worker_arxiv_request_state` | Atomic source-stage claim and one-use permit, then safe-close/status recovery. Fresh grant returns `job`, `token`, `byte_ceiling`, `request_deadline`, and optional `reservation`. Every replay returns `granted=false` |
| `worker_reserve_original` / `worker_original_reservation` / `worker_publish_original` | Reserve storage/transfer and fixed path; inspect uncertain upload; publish verified global state once. These never restore account membership |
| `worker_claim_original_verification` / `worker_original_verification_state` / `worker_record_original_verification` | Durable `pending_verification` claim, fixed byte/profile request, and immutable authenticated verifier result. Publication requires this evidence; a transfer worker cannot bypass it |
| `worker_claim_asset_projection` / `worker_project_import_acquisition` / `worker_project_library_availability` | Claim a bounded fanout pass, then reconcile **one account** at a time against current intent/current availability. Commit the projection and library sequence together |
| `worker_scan_acquisition_jobs(after_id?, limit=50, kind?)` / `worker_scan_original_verifications` / `worker_scan_asset_projections` | Bounded retained-state queue discovery; `kind=lookup` excludes disabled original work from metadata scheduling. Continue every page and restart after each complete pass; enqueue acknowledgement is only a hint |
| `worker_claim_original_orphans` / `worker_confirm_original_deleted` | Fence only unpublished expired reservations; bounded exact-path deletion; release capacity only on confirmed absence |

The old split `worker_begin_arxiv_request` and `worker_mark_original_uploading` endpoints have no execution grants and only typed failure stubs. They cannot bypass atomic admission. A metadata-only scheduler uses both scan filters; it does not invent a source-only decision or create disabled original work just to remove an eligible row from its queue. The final interest check and read-only enable/profile/cap refresh follow admission/window locks, so a Cancel or operator disable committed while the grant transaction waited prevents new authority. No policy row lock is taken under the gate/job. A change racing after this final check belongs to the already-admitted bounded invocation; disabling/draining waits beyond its recorded hard horizon before changing runtime lifetime assumptions. A cancellation after a valid grant still permits only that bounded free transfer.

Service current-state/claim endpoints are essential: 010's checkpoint API has compare-and-set arguments but is not a work claim, and a lost checkpoint response is not permission to start over. A 010 compare-and-set failure triggers `worker_import_state`; it does not trigger an unfenced retry with whatever revision was most recently seen. Check the original operation/intent and pinned job before proceeding.

Discovery/linking is deliberately recoverable across two transactions. A global job can exist before an account link succeeds; jobs without current interests cannot start new source traffic and expire within bounded capacity. If linking succeeds but the response is lost, scan/status returns the existing relationship. Never hold the account transaction while obtaining a global job or doing network I/O.

Every lookup/original checkpoint advances its committed job revision. The bounded reconciliation scan compares that revision with each interest's last-projected revision, so source-only and failure completions also have a durable projection obligation without requiring a document or a Realtime delivery. The account transaction advances the appropriate projected revision only after applying or explicitly rejecting the result against current intent. A newly linked interest must inspect an already-complete job. A stale old interest is retired, not applied to a new Retry intent merely because its import ID still matches.

Lookup stages are `atom → pin_metadata → license → complete`; completion records either eligible evidence or source-only. Original stages are `reserve → download/upload → pending_verification → verifying → publish → complete`. Both also have `retry_wait`, `no_interest`, `blocked`, and `failed` statuses. Store the failed stage, attempt count, and next deadline; do not encode every combination in the client import phase. Proposed automatic limits are three metadata attempts per stage and two original-download attempts per job over 24 hours, with backoff and the shared rate gate. Verification attempts have a separate fixed cap. All error/status strings are enumerated and bounded.

`v2_retry_import` remains an explicit retry of a retryable failure and retains the original accepted Add/removal fence. It captures a new interest revision; it may use verified earlier stage outputs or a newly bounded job generation. It does not turn `source_only` or `membership_conflict` into a retry, silently select a newer paper version, reset global rate limits, or re-enable OCR. An explicit Add again is a new operation using a caught-up observed cursor.

## Availability and library synchronization

Global availability and account library projection are different records. An asset request checks authoritative current availability immediately. The library shows its last committed projection until durable catch-up arrives. **Never make `library_item_entry` join changing global availability while retaining the old item `state_seq`.** Equal sequences must represent equal payloads; native reconciliation now relies on that invariant.

011 adds stored `original_availability` and `render_availability` fields while retaining existing 010 identifiers, paging shapes, and operation receipt semantics. Original values are `available`, `unavailable`, `quarantined`, and `unverified`; render values additionally include `not_converted` and `incompatible`. Both include their applied availability revision. Derive `readiness` from this committed projection: `converted_ready` for an available compatible complete render, otherwise `pdf_ready` for an available original, otherwise `unavailable` when approved/pinned bytes cannot currently be used, otherwise `unverified`. `artifact_id` remains the chosen pin even when its bytes are unavailable; do not erase it or choose another renderer as a fallback. Complete render-bundle availability will be established by 012, not inferred from a manifest object alone. Deploy tolerant native/web readers and exercise unknown-state/old-client fixtures before enabling new states; this is an explicit compatibility gate, not an assumption that old enums accept new values.

The projection write holds the account, document, library policy, and sync-state locks in the established order. The service-only availability projector also updates closed-account rows, without authorizing membership activity, so one closed recipient cannot block later fanout. Import projection retains both job/output snapshots captured before policy; a new document/approval appearing while it waits is handled by the next revision scan, never by a new document lock after policy. It reads current availability and current membership, preserves all pins and removal fences, changes only a materially changed projection, then increments `state_seq` and emits the full item entry atomically. It does not advance `membership_revision`, `last_intent_seq`, or `last_remove_seq`. Removed items remain removed; retain their projection/tombstone identity. Import phase/mapping updates similarly use the current captured `intent_revision` and 010 checkpoint/resolve rules.

New or restored membership must snapshot current availability while holding the same document serialization boundary used by availability transitions. This is necessary even if a fanout pass already scanned past that account. Pin additions also change `state_seq` and emit a journal entry. Backfill every 010 item, including removed items and closed accounts, with a new state sequence and full delta. The migration first locks the accounts table and library-policy row before any FK DDL; this drains both account writers and global catalog writers before taking their referenced-table locks. No applied migration is edited.

The coalescing outbox records a durable dirty document in the transaction that changes availability. Assign revisions from the committed environment asset-state sequence under paper capacity; do not compare unrelated per-object counters to find a document's latest change. A pass uses a stable `(account_id, item_id)` scan cursor over retained membership rows and bounded pages. It applies **latest** state, not the historical state that originally dirtied the row. Confirm each account commit/status before advancing the pass cursor. If the target changes during a pass, finish/restart as needed from the beginning; clear the dirty row only when the unchanged target has been fully visited. A crash after an account commit repeats an idempotent comparison. New subscribers read current availability on creation. Rapid changes coalesce without dropping the obligation or creating an unbounded row per notification.

Fanout must not need another customer command receipt or a new growth allowance to report a missing file. Reserve journal capacity through 010's existing compaction/resync mechanism; a slow client may need a baseline, but current rows and removal fences survive. Native and web continue to merge by entity `state_seq`, finish creation-bounded baseline pages, then catch up from `baseline_cursor`. A baseline is still current rows within a creation cutoff, not a historical snapshot.

## Lock order and transaction boundaries

The implementation review must enumerate **row, unique-index, and foreign-key locks** for every new/changed RPC, including calls into 010 helpers. Network I/O is outside every transaction. Use a fixed ordering among multiple documents/objects, and avoid holding more than one account lock.

| Transaction family | Required order |
|---|---|
| Lookup scheduling / metadata checkpoint | Acquisition policy/capacity → source slot/job → library catalog policy only if recording metadata; no document or account mutation afterward |
| Original reservation | Paper capacity → original job → reservation/step; no account lock or document publication afterward |
| Verification claim/result | Paper capacity → original job → reservation → verification request/result; no account or catalog lock afterward |
| Global original publication / availability change | Paper capacity → document (or serialized exact-hash insertion) → original job where needed → reservation/object → catalog/library policy if creating approval → dirty outbox |
| Import interest / library projection | Request windows where applicable → one account `NO KEY UPDATE` → document `KEY SHARE` if known → library policy → sync state → interest/projection; no global acquisition/paper-capacity lock afterward |
| Metadata source claim + permit | Gate → lookup job `NO KEY UPDATE` → matching step → transfer-capacity/window rows; read policy only, no account/catalog lock afterward |
| Original source claim + permit | Paper capacity → gate → original job `NO KEY UPDATE` → owned reservation `NO KEY UPDATE` → matching step → transfer-capacity/window rows; extend `safe_after` only with a new grant |
| Network safe-close/status | Gate → matching step → transfer-window rows; no job/account/catalog mutation; unknown old ceilings stay charged until proved closed |
| Original read grant | Read-policy mutex → account → document → transfer-capacity/window rows; no library policy or paper capacity afterward |
| Orphan claim / confirmation | Paper capacity → owning job → reservation; no account or catalog mutation |

Use `FOR UPDATE` on the document as the global availability/publication serialization boundary, so it conflicts with account-side document `KEY SHARE`. Merely reading an availability row without this ordering leaves a create-after-fanout race. A metadata job that has taken its job lock cannot later enter a publication path that first requires a document lock; release and call the separately ordered publication RPC.

Existing acquisition job/source-slot identity rows use **`FOR NO KEY UPDATE`** for mutable state. Their referenced identity keys remain immutable. An account linker already holds `library_policy` when its interest FK takes `KEY SHARE` on a job; a global job holder must not use a conflicting `FOR UPDATE` and then wait for that same policy. Apply the same review to original-object/reservation/verification identity rows: use `NO KEY UPDATE` for lifecycle fields where account/catalog FKs can take `KEY SHARE`, and never update referenced keys. New `stored_objects` inserts acquire document FK locks only after the document boundary. Immutable approvals/profiles/artifacts need no mutable `FOR UPDATE` lock. Document `FOR UPDATE` remains the deliberate exception, always acquired before `library_policy`. Test the actual FK insertion schedules, not only direct row updates.

Keep public global jobs free of account-owned foreign keys. Account interest links are installed in the account transaction; creation of the global job and quota admission happen separately. Updating interest rows or inserting account FKs must not unexpectedly acquire an account lock inside the global publisher. Foreign-key locks on job references must also be checked against publisher/retirement ordering. Do not delete referenced jobs as a cleanup shortcut.

The future 012 paid path starts with budget locks, then paper capacity when needed, the funding account, document, logical work, provider attempt/objects. Its account fanout remains separate. 011 must not introduce an inverse path from an account, document, job, or library policy back to paper capacity or budget. Test contention against the still-present legacy OCR observation RPC as well as new endpoints.

## Candidate beta limits and retention

These are conservative **disabled candidate defaults**, not subscription allowances or proof of fitting the $100/month total. Reconcile them with fixed infrastructure, backup, support, encrypted-history, and future Mathpix commitments before enabling workers. All growth caps fail closed without deleting command receipts, membership/removal fences, or verified assets.

| Resource | Candidate default / accounting rule |
|---|---|
| Imports | Keep 010's 10 active per account / 100 per environment, 2,000 retained imports per account / 20,000 environment |
| Source lookup slots / acquisition jobs / steps | 2,000 / 10,000 / 100,000 retained rows per environment; also cap combined job/step JSON at 32 MiB; ≤8 KiB per stored result/evidence payload |
| Verification profiles/results | 32 retained immutable profiles, ≤3 verification attempts/results per reservation, ≤8 KiB each; count their JSON in the same 32 MiB control-data budget |
| Interests | One bounded current row per retained import; old generations remain fenced by immutable 010 commands and step identities |
| Source traffic | One global connection; at least 3 seconds between starts; 1,000 source requests/day environment, including retries/redirects; bounded per-account new-work request windows |
| Original reservations | Four concurrently transferring/verifying originals per environment; one arXiv connection still applies; pilot maximum 5 MiB/50 pages, profile disabled until validated |
| Retained original storage | 512 MiB and 2,000 objects per environment, counting reservations at their maximum until safely shrunk and including all uncertain/deleting bytes |
| Source-download traffic | 1 GiB/month environment, charging bounded attempts including failed reads; reserve before starting |
| Storage verification/read traffic | Separate worker verification and customer-read counters; proposed 2 GiB/month each per environment and 256 MiB/month customer reads per account |
| Lookup/original retry | Three metadata attempts per stage, two source-PDF attempts, bounded verification attempts, maximum 24-hour automatic retry age; manual/customer retry still consumes global limits |
| Unpublished reservation expiry | 24 hours, followed by old-invocation grace and exact-path reconciliation; expiry never reclaims a published object |

The SQL must specify UTC window rollover and reservations surviving a rollover; it cannot reset or forget an uncertain transfer when the month changes. Attribute reads conservatively when actual sent bytes are unknown. Retained transfer-window rows have an independent 10,000-row cap; no automatic history deletion resets charges. Record actual bytes as well as charged ceilings, without claiming these counters equal every byte of a platform invoice. Lowering a cap below existing use rejects new growth and keeps reconciliation, removals, and essential status available. Reserve work-completion/status headroom when admitting a job; exhausted receipt/JSON capacity must not strand publication or orphan confirmation. Use deterministic small-cap tests, not production-sized stress alone.

Concrete control-data admission rule: reserve 12 step slots per lookup job and 24 per original job, plus the fixed job envelope, all at the 8 KiB maximum. These are logical JSON/envelope admission bounds, not an estimate of PostgreSQL page/index/WAL overhead. Prepare-command receipts and profile envelopes count too; original jobs retain their admitted slots through terminal cleanup. Consume that reserved allowance for bounded network/storage/verification attempts and their results; reads/replays do not allocate more rows. At least the terminal result slot and two cleanup slots per allocated unpublished reservation stay unavailable to further retry growth. Unused general slots/bytes can be released on terminal completion, but each unfinished reservation retains its cleanup slots/bytes until deletion or publication is confirmed. A cap reduction does not revoke an existing reservation. Deny another retry before it could spend these obligations; fail durably through the reserved terminal slot. This headroom counts against both the 100,000-step and 32 MiB limits, so many small or uncertain jobs cannot exhaust space needed to finish earlier work.

Initially collect **only unpublished expired uploads and losing duplicate uploads**. Fence the reservation `deleting` first; wait out possible old uploaders; delete its exact server-generated path; confirm absence; then release capacity. Do not sweep arbitrary bucket prefixes, infer orphanhood from a missing client, or release capacity after a merely attempted deletion.

Published originals and converted assets are retained. 010 approvals permanently reference their original object IDs, and artifacts reference fixed manifests; deleting their physical files and making a new object later does not repair those pins. Published eviction/restoration needs a future explicit replica/availability model, retention policy, and backup coordination. Until then, refuse new capacity when full. Unexpected missing/corrupt published bytes set availability and enqueue fanout; they do not authorize rewriting identities or quietly redownloading over the path.

Current backups include bytes for `stored_objects` marked `verified`; a pending acquisition reservation is not a backed-up file. After restore, leave outbound and publication disabled, reconcile unfinished jobs/reservations against actual storage, and restart only safe uncompleted stages. A restored pending-verification or claimed row is not evidence of a present object or an ended external invocation. Published originals must enter the verified-object backup set atomically with publication. See [backup/restore contract](BACKUP_AND_RESTORE.md).

**Pinned retry:** `worker_retry_lookup` copies a failed lookup's metadata/version/full Atom instants into a new bounded job. A license-stage retry starts at license, and cannot become the shared latest-cache answer. The account must first issue its explicit 010 retry and link the new captured intent. Ordinary original retries get a fresh original job only after the old job is terminal. Orphan retirement terminalizes unfinished last-candidate work, but never changes a completed reuse job or turns a permanent verifier rejection into a retryable download failure.

**Verifier authority:** `science_reader_pdf_verifier` is a dedicated `NOLOGIN` role with only scan/claim/status/result/transient-read/integrity-failure RPC grants. `PUBLIC`, `anon`, `authenticated`, and `service_role` cannot call those RPCs. Acquisition service callbacks cannot assert page counts. The claim returns an `execution_deadline` and a reporting lease ending 120 seconds later. Parsing must stop at the execution deadline; negative results can still be reported within the current generation's reporting authority. Successors wait for that authority to expire. Stale generation/profile/build evidence cannot publish.

The immutable profile selects one strict resource-evidence mode. `measured` requires actual per-call CPU, elapsed time, peak whole-host memory, and WASM bytes. `hard_limits` requires attested CPU/memory **limits**, elapsed time, WASM bytes, and the profile's pinned host-enforcement digest; it rejects measured-peak fields. That digest must describe the reviewed deployment/runtime, CPU scope, memory accounting boundary, hard termination, reporting/reconciliation behavior, and concurrency limit. A V8/external memory snapshot is not OS peak RSS; isolate aggregate CPU is not per-call CPU. Neither mode lets a callback label itself an admitted host. The local qpdf/WASM prototype and Supabase's published platform limits alone do not satisfy hosted admission. The prototype remains `hosted_admitted:false`; no synthetic CPU or peak values may be supplied to make it pass.

**Original reads:** `v2_original_descriptor(item_id)` authorizes current membership and live evidence/availability, returning safe object/hash/length/media/page/profile/availability data and a UTC `read_day`, without a bucket path. The trusted proxy calls `worker_authorize_original_read(account,item,operation,day,first,last)`; it verifies the authenticated account at ingress, then SQL rechecks membership/live availability and atomically charges the full requested range. Only a newly granted result contains the private path and 120-second authority. Replay never grants another transfer. Same-day receipts cap at 100 per account/1,000 environment, retain today and yesterday, and old days cannot create new authority after cleanup. Unknown/failed sends keep their charge. Transfer counters survive receipt/account cleanup. The proxy implementation, entitlement policy, HTTP Range/ETag semantics, one-use execution, and runtime egress evidence are still missing; SQL does not make signed Storage URLs safe for this purpose.
