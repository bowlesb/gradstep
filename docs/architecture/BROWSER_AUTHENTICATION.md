# Browser authentication

Status: implementation in progress (2026-10-08). Design reviewed before implementation. Local protocol/UI evidence and provider readiness are separate; this document does not claim hosted Google or Apple acceptance.

## Authority and storage

`backend.ts` remains the only session and refresh-token owner. Email and provider sign-in share its bounded, no-redirect REST transport. The existing environment session key becomes one versioned envelope containing exact backend/environment, a random boundary, `session: Session | null`, and optional OAuth attempt/phase. One `localStorage.setItem` publishes the complete record; one short cooperative Web Lock serializes new-client authority changes. Refresh retains boundary and login lifetime and its existing single refresh owner. Sign-in, sign-out, method abandonment and attempt replacement retire the boundary; the in-memory generation/signal retires even for signed-out to signed-out changes.

Ordinary startup may explicitly adopt a bounded, validated legacy raw Session, preserving its login lifetime. Callback handling runs before that adoption or absent-record initialization and accepts only its exact existing envelope. Malformed/future records preserve their bytes and refuse writes. No callback creates a replacement for a missing or overwritten boundary. Legacy raw login/removal therefore invalidates a pending return, including login then logout while the tab is away. Delayed raw/removal storage events retire local authority even if storage already contains a newer value. Atomic record writes do not provide compare-and-swap against an arbitrary older writer that ignores Web Locks; no such claim is made. [HTML storage concurrency](https://html.spec.whatwg.org/multipage/webstorage.html#introduction).

Successful persistence and exact readback precede publishing accepted credentials. A failed login write accepts nothing. Sign-out hides/aborts the old session immediately, then persists a fresh signed-out envelope; removal is the fallback if the write fails. If both fail, report failure accurately and keep this page's authority retired. Credentials retained on disk after a failed removal are not represented as durably signed out. Keys use the same validated persisted-authority check inside existing IDB writer fences. Podcast/account scopes continue to use generation, signal, account UUID and unchanged login lifetime; no second credential or podcast storage owner is introduced.

## Same-tab PKCE lifecycle

Google and Apple use one code-only S256 flow. A 32-byte random verifier and one random attempt ID are held in a bounded versioned `sessionStorage` record with provider, exact backend/environment, exact app origin and `/auth/callback`, creation/expiry and captured boundary. This necessary full-redirect persistence is tab-scoped and contains no code, email or session tokens. Attempts expire after ten minutes, reject backward clock movement, and never resume an already claimed exchange.

The redirect target is the existing exact callback URL, without a nonce query or fragment. Supabase binds the returned code to the verifier; an old unknown code can fail this one exchange but cannot authorize a different attempt. No hosted allowlist expansion is implied. Callback validates the complete destination, rejects fragments/token fields and duplicate/malformed codes, scrubs the URL synchronously, and checks the local attempt against the persisted envelope. Under the auth lane it claims that attempt once and removes the stored verifier before a bounded token exchange. Reload during exchange requires a new explicit start. Exchange success and failure recheck boundary/attempt/account after HTTP before changing authority. No exchange is automatically retried. [Supabase PKCE](https://supabase.com/docs/guides/auth/sessions/pkce-flow).

Starting another method, cancellation, Back to the app, sign-out or another tab's login cannot let old preparation/exchange publish later. Codes, raw callback URLs, verifier, tokens and provider bodies never appear in diagnostics. Finite local errors explain cancelled/expired/unavailable/storage/connection outcomes. Account UUID is authoritative; optional email is display only. Existing key recovery remains independent from account sign-in.

## Provider readiness and evidence

Google and Apple share client protocol code. Each has a separate explicit browser capability; Apple native configuration cannot enable the browser button. Apple web requires its reviewed Services ID/domain/callback/secret lifecycle. Production configuration is untouched by this implementation. [Google browser setup](https://supabase.com/docs/guides/auth/social-login/auth-google), [Apple browser setup](https://supabase.com/docs/guides/auth/social-login/auth-apple).

Local verification covers strict callback/PKCE vectors, consumed and abandoned attempts, storage failures, other-tab login/logout/new lifetime while away and during exchange, delayed legacy notifications, bounded legacy adoption, account/key scope, same-tab fake-provider journeys and exactly one token exchange. Real provider first/returning sign-in, cancellation, sign-out/restart and recovery remain dedicated hosted acceptance gates.
